# Спека: проверка секретов перед коммитом

Источник: `ai/9/task.md`, решения grilling-сессии 2026-10-30, замеры gitleaks v8.30.1 на этом репозитории и в одноразовом репозитории.

## Problem Statement

Репозиторий `github.com/MikhailEpatko/gms` публичный. Сейчас перед коммитом pre-commit hook проверяет только код (gofmt, vet, тесты), а содержимое коммита на секреты не смотрит никто. Секрет может попасть в коммит разными путями: токен GitLab вставлен в тест или README, строка `HTTPS_PROXY` с паролем корпоративного прокси скопирована из `~/.zshrc` в документацию или память, кусок настоящего `~/.config/gms/config.json` с корпоративным хостом GitLab и путями репозиториев оказался в тесте или файле задачи. После `git push` всё это становится публичным, и откатить утечку уже нельзя: можно только сменить пароль. Push protection на GitHub включён, но он знает только токены известных провайдеров. Пароль в URL и корпоративный хост он пропускает.

Коммиты делают и человек, и агент. Агент, получив отказ hook, может сам его «починить»: сделать коммит с `--no-verify` или добавить исключение. А то, что hook печатает, попадает в контекст и логи сессии агента.

## Solution

Pre-commit hook первым шагом проверяет индекс на секреты с помощью gitleaks и не пускает коммит, если что-то нашёл. Проверяется ровно то, что попадёт в коммит. К правилам gitleaks по умолчанию (токены провайдеров, приватные ключи, энтропия) добавлены два своих правила: учётные данные в URL и URL ветки с настоящим хостом GitLab. В выводе hook показаны файл, строка и правило, а сам секрет заменён на `REDACTED`. Если gitleaks не установлен, коммит тоже не проходит, а hook подсказывает команду установки. Агенту запрещено обходить hook и добавлять исключения без подтверждения пользователя.

```
$ git commit -m "docs: прокси"
Finding:     export HTTPS_PROXY=http://ivanov:REDACTED:3128
Secret:      REDACTED
RuleID:      url-credentials
File:        README.md
Line:        42
...
WRN leaks found: 1
коммит остановлен: в индексе найден секрет (см. выше).
...
```

## Implementation Decisions

**Инструмент.** gitleaks v8.30.1, модуль `github.com/zricethezav/gitleaks/v8`. Репозиторий проекта переехал в `gitleaks/gitleaks`, а путь модуля остался прежним. В `go.mod` gitleaks не добавляется: директива `tool` втащила бы его зависимости в модуль, а правило проекта — «сторонних зависимостей нет». Hook ищет `gitleaks` в `PATH` и версию не проверяет: у бинарника, собранного через `go install`, `gitleaks version` печатает `version is set by build process`, проверять нечего. Версия закреплена только в команде установки.

**Hook.** Pre-commit hook из `.githooks/` выполняет два шага по порядку:
1. Если `gitleaks` нет в `PATH`, hook печатает в stderr `gitleaks не найден, установите: go install github.com/zricethezav/gitleaks/v8@v8.30.1` и завершается с exit 1.
2. Если в корне есть `.gitleaksignore`, hook печатает в stderr `удалите .gitleaksignore: исключения оформляются через gitleaks:allow в строке или allowlist своего правила в .gitleaks.toml` и завершается с exit 1, даже если секретов в индексе нет. gitleaks сам читает этот файл из корня, в том числе неотслеживаемый, и молча пропускает перечисленные в нём находки. Флаг `--gitleaks-ignore-path` это не отключает (проверено на v8.30.1).
3. Индекс проверяется в режиме `git` с флагами `--pre-commit --staged`, вывод замаскирован (`--redact`) и подробный (`-v`, без него gitleaks печатает только число находок), баннер выключен. Конфиг передаётся явно путём из корня репозитория (`--config`), поэтому `GITLEAKS_CONFIG` и текущий каталог на правила не влияют. Конфиг читается из рабочего дерева, а не из индекса: неиндексированная правка конфига по риску такая же, как правка самого hook. Если gitleaks завершился не с 0 (найдены секреты или сломан конфиг), hook печатает в stderr подсказку и завершается с exit 1. Подсказка:
   ```
   коммит остановлен: в индексе найден секрет (см. выше).
   уберите его из индекса, а если это ложное срабатывание, добавьте gitleaks:allow в строку
   или заглушку в allowlist своего правила в .gitleaks.toml.
   ```
4. Только после этого запускается `scripts/check.sh`, как сейчас.

Сам `scripts/check.sh` не меняется и gitleaks не вызывает: он проверяет код рабочего дерева, а секреты проверяются в индексе.

> Пересмотрено после ретро 2026-10-31 (ADR 0004): hook запускает `check.sh` на копии индекса, а `check.sh` вызывает `scripts/check-secrets.sh` (случаи правил, hook, файлы репозитория). Ручная приёмка из Testing Decisions заменена этим скриптом.

**Конфиг gitleaks** лежит в корне репозитория. Он расширяет правила по умолчанию (`useDefault`) и добавляет два своих правила. Корпоративный домен в конфиге не упоминается.

- **`url-credentials`, учётные данные в URL.** Ловит `схема://логин:пароль@хост`. Секрет — пароль вместе с хостом (`пароль@хост`): в выводе hook не видно ни пароля, ни хоста прокси или корпоративного GitLab. Логин непустой, без пробелов, `/`, `:`, `@` и кавычек. Пароль идёт от `:` до последнего `@` перед хостом, без пробелов и `/`, и может содержать `@`, `:` и кавычки (`P@ssw0rd`, `it's…`). Хост состоит только из букв, цифр, `.`, `-` и `_`, поэтому скобки, `>`, `*`, кавычки и знаки препинания после URL (ссылки и выделение в Markdown) в него не попадают. Исключение действует, если выполнено хотя бы одно:
  - пароль **целиком** равен заглушке: `pass`, `password`, `пароль` или маске gitleaks `REDACTED` (она стоит в любом примере вывода hook) без учёта регистра, заглушке в угловых скобках (`<password>`, `<пароль>`), переменной окружения `$ИМЯ` из заглавных букв, цифр и `_` или подстановке `${имя}`;
  - хост — домен-пример (`example.com`, `example.org` и их поддомены) без учёта регистра, в том числе с точкой конца предложения.

  Исключение проверяется по паролю или хосту целиком, а не по подстроке. Механизм stopwords gitleaks ищет подстроку, и с ним `S3cr3tPassw0rd77` прошёл бы из-за `pass`. Поэтому stopwords здесь не используются. Логин в исключении не участвует: `user` сам по себе URL заглушкой не делает. gitleaks склеивает регулярки одного allowlist через `|`, поэтому флаг регистра ставится только на группу (`(?i:…)`): с `(?i)` в начале первой регулярки регистронезависимыми стали бы все, и `$ecr3t…` прошёл бы как `$ИМЯ`.
- **`gitlab-tree-url`, URL ветки с настоящим хостом.** Ловит `http(s)://[логин@]хост[:порт]/…/-/tree/…`, то есть формат URL из конфига `gms`, со схемой в любом регистре. Секрет — всё между `://` и `/-/tree/`: логин, хост, порт и путь к репозиторию. В выводе hook весь этот участок заменён на `REDACTED`, так что ни хост, ни группы и репозитории не видны. Исключение — хост-заглушка: хост целиком, без учёта регистра, равен `gitlab`, `gitlab.com`, заглушке в угловых скобках (`<host>`, `<gitlab-host>`) или домену-примеру (`example.com`, `example.org` и их поддомены). Похожие хосты (`gitlab.example.com.corp-internal.ru`, `mygitlab`) ловятся. Ссылки на другие страницы GitLab (MR, pipeline, blob) правило не ловит, и это осознанно (см. Out of Scope).
- **Заглушки хоста в обоих правилах общие**: `<…>` и домены-примеры, а в URL ветки ещё `gitlab` и `gitlab.com`. Тот, кто пишет документацию, держит в голове одно соглашение.

**Исключения.** Допустимы два механизма: allowlist своих правил в конфиге (для систематических заглушек) и `gitleaks:allow` в той же строке (для единичных случаев). `.gitleaksignore` не заводится, а если он появился в корне, hook отказывает (см. шаг 2 hook). Расширять allowlist правил по умолчанию не разрешается.

**Правило для агента** (CLAUDE.md, рядом с описанием hook):
- не делать `git commit --no-verify` и не обходить hook иначе (подмена `core.hooksPath`, `.gitleaksignore`, правки hook или конфига ради обхода);
- не добавлять `gitleaks:allow` и не менять allowlist самостоятельно;
- при срабатывании остановиться и сообщить пользователю файл, строку и `RuleID`, не повторяя секрет;
- исключение добавляется, только если пользователь подтвердил ложное срабатывание.

**Документация.**
- **README, раздел «Сборка из клона»**: блок «перед первым коммитом» с двумя командами, `git config core.hooksPath .githooks` и `go install github.com/zricethezav/gitleaks/v8@v8.30.1` (как альтернатива `brew install gitleaks`). Одна фраза: hook не пустит коммит с секретом. Ещё одна: push protection на GitHub — второй рубеж только для токенов известных провайдеров. Команда установки gitleaks живёт только в README и в сообщении hook.
- **CLAUDE.md, раздел «Команды»**: строка про hook дополняется (сначала gitleaks по индексу с конфигом из корня, затем `check.sh`), рядом правило для агента.
- ~~**Комментарий в hook** описывает оба шага и способ подключения.~~ Заменено ADR 0005: в hook нет комментариев, оба шага описаны в ADR 0004 и README, способ подключения — в README, раздел «Сборка из клона».
- **`ai/4/task.md`**: в «Открытые вопросы» и «Связи» добавлен пункт о сканировании истории gitleaks с конфигом из этой задачи.

**Настройки GitHub** не меняются: secret scanning и push protection у репозитория уже включены, `non_provider_patterns` остаётся выключенным.

## Testing Decisions

- **Seam один: `git commit` в одноразовом клоне репозитория с подключённым hook.** Это самая верхняя точка: проверяется ровно то, что видит человек или агент при коммите, то есть создан ли коммит, код выхода и текст в stderr. Регулярки правил отдельно (через `gitleaks stdin`) не проверяются. Пересмотрено (ADR 0004): правила проверяются отдельно одним запуском `gitleaks dir` в `scripts/check-secrets.sh`, сквозные случаи hook лежат там же. Производственный код `gms` и Go-тесты задача не трогает.
- **Приёмка ручная**, автотеста на правила нет: регулярок всего две и меняются они редко, а тест сделал бы gitleaks обязательным для `check.sh` и CI. Кто правит конфиг gitleaks, повторяет список случаев руками. Пересмотрено (ADR 0004): приёмку заменил `scripts/check-secrets.sh`, его вызывает `check.sh`.
- **Случаи, при которых коммит не создаётся.** Exit ≠ 0, в выводе есть `File`, `Line` и `RuleID` нужного правила, секрет заменён на `REDACTED`, `check.sh` не запускался, после вывода gitleaks идёт подсказка hook:
  1. файл с токеном `glpat-` + 20 символов → правило gitleaks по умолчанию;
  2. `HTTPS_PROXY=http://ivanov:S3cr3tPassw0rd77@proxy.corp.local:3128` → `url-credentials` (проверяет, что `pass` внутри пароля не делает его заглушкой); <!-- gitleaks:allow -->
  3. `http://user:RealPassw0rd@proxy.corp.local:3128` → `url-credentials` (проверяет, что логин `user` заглушкой не делает); <!-- gitleaks:allow -->
  4. JSON-конфиг с URL ветки `…/grp/p1/-/tree/dev` на выдуманном хосте `gitlab.corp-internal.ru` → `gitlab-tree-url`;
  5. `gitleaks` убран из `PATH` → сообщение с командой установки, gitleaks не запускался.
  6. Неотслеживаемый `.gitleaksignore` в корне с отпечатком находки из случая 1 → сообщение `удалите .gitleaksignore…`. Тот же отказ и при индексе без секретов.
  7. URL с паролем, в котором есть `@`, `:` или апостроф, с паролем из `$`, строчных букв и цифр, и такой URL в ссылке Markdown на настоящем хосте → `url-credentials`. Пароль замаскирован целиком, ни одна его часть в выводе не видна.
- **Случаи, при которых коммит проходит в `check.sh`** (gitleaks без находок):
  1. `http://user:pass@proxy:3128`, `http://user:password@proxy:3128`, `http://user:PASSWORD@proxy:3128`, `http://user:${PROXY_PASSWORD}@proxy:3128`, `http://user:<password>@proxy.corp.local:3128`, `http://ivanov:REDACTED@proxy.corp.local:3128`, `http://логин:пароль@хост`, `http://ivanov:pw@proxy.example.com:3128`, `[прокси](http://ivanov:pw@Proxy.Example.com).`;
  2. URL веток на `gitlab.example.com`, `git.example.com`, `example.org`, `https://gitlab/…`, `https://<host>/…`, `https://<gitlab-host>/…`, `HTTPS://GITLAB.COM/…`, с логином (`user@gitlab.example.com`) и портом;
  3. строка случая 2 из предыдущего списка с `gitleaks:allow`;
  4. обычный коммит без секретов.
- **Подмена конфига**: при `GITLEAKS_CONFIG`, указывающем на пустой конфиг, случай 2 из первого списка всё равно ловится.
- **Вся история**: полная проверка истории репозитория в режиме `git` с новым конфигом находок не даёт.
- **Документы задачи** коммитятся через hook без находок. Выдуманные примеры, которые нарочно похожи на настоящие, оформлены одним из двух способов. Первый — пометка `<!-- gitleaks:allow -->` по подтверждению пользователя (пароли в URL из тикета 2). Второй, предпочтительный, — описание словами без полного URL, например «URL ветки `…/-/tree/dev` на хосте `gitlab.corp-internal.ru`», которое правило не ловит, и исключение тогда не нужно.
- **`scripts/check.sh`** проходит как раньше.
- Fake-секреты для приёмки существуют только в одноразовом клоне и в репозиторий не попадают.

## Out of Scope

- Шаг gitleaks в CI: это задача 4, сюда входит только пометка в `ai/4/task.md`.
- Изменение настроек GitHub, в том числе включение `non_provider_patterns`.
- Автотест правил gitleaks и вызов gitleaks из `scripts/check.sh` (сделано позже, ADR 0004).
- Отдельный выключатель `check.sh` с сохранением проверки секретов.
- Проверка версии gitleaks в hook.
- `.gitleaksignore` и baseline-файлы.
- Правила против других ссылок на корпоративный GitLab (MR, pipeline, blob) и против любого хоста не из белого списка.
- URL ветки с IPv6-литералом (`https://[fd00::1]/…`) и с экранированными `\/` в JSON.
- Переписывание истории: история уже чистая.
- Перенос пароля прокси из `~/.zshrc` в Keychain: это настройка машины пользователя, а не репозитория.
- Проверка неотслеживаемых и игнорируемых файлов (`.remember/`, `.idea/`, бинарник `gms`) в hook. С ADR 0004 `check.sh` проверяет неотслеживаемые неигнорируемые файлы рабочего дерева, игнорируемые по-прежнему нет.

## Further Notes

- Замеры 2026-10-30. Сборка gitleaks через `go install` занимает ~2 мин. Вся история (6 коммитов) проверяется за 0,7 с, находок нет. Homebrew ставит ту же версию 8.30.1 готовой сборкой.
- С правилами по умолчанию gitleaks поймал `glpat-…` в индексе, но пропустил и пароль в URL прокси, и URL ветки с корпоративным хостом. Поэтому и понадобились два своих правила.
- У репозитория включены `secret_scanning` и `secret_scanning_push_protection` (проверено через API GitHub). Свои шаблоны GitHub позволяет задавать только организациям, у личного репозитория их нет. Поэтому пароль в URL и хост ловятся только локально.
- ADR не нужен: сканер легко заменить, а решение не удивит читателя без контекста. Пересмотрено: проверка `check.sh` на копии индекса и случаи правил в `check.sh` записаны в ADR 0004. В GLOSSARY.md ничего не добавляется: секреты относятся к инструментам разработки, а не к предметной области `gms`.
- При обновлении версии gitleaks её меняют в двух местах: в README и в сообщении hook.
- Сам `.gitleaks.toml` gitleaks не проверяет: глобальный allowlist по умолчанию исключает пути с `gitleaks.toml`. То, что в конфиге нет корпоративного домена и настоящих хостов, проверяет ревьюер, а не hook.
- Остаточный риск из правил по умолчанию (проверено на v8.30.1). Глобальный allowlist gitleaks начинается с `(?i)^true|false|null$`, а склейка через `|` делает регистронезависимым его целиком. Поэтому любой секрет любого правила, который содержит `false`, начинается с `true`, кончается на `null` или состоит из `$` и одних букв (`$ecretPassword`), пропускается молча. Для `gitlab-tree-url` это хосты вроде `trueconf.…` или `…false…`. Убрать глобальный allowlist, сохранив `useDefault`, нельзя. Для этого пришлось бы держать в репозитории копию всех правил по умолчанию, и это решение не принято.
