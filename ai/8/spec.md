# Спека задачи 8: публикация бинарников в GitHub Releases

## Problem Statement

`gms` ставится только через `go install`, и каждому пользователю нужен Go 1.27+ — хотя Go нужен только для сборки, а не для работы утилиты. README прямо говорит «Готовых бинарников нет». Тегов и релизов в репозитории нет. Бинарники без подписи, но `gms` запускается один раз на вывод, так что карантин macOS и прогон неподписанного файла антивирусом — приемлемая плата.

## Solution

Отдельный релизный workflow `.github/workflows/release.yml` (US17 спеки задачи 4): push тега `v*` запускает проверку (`sh scripts/check.sh`), затем сборку матрицы из 6 целей `GOOS`/`GOARCH` — по паре на каждую платформу из «Системных требований» README — и публикацию GitHub Release с голыми бинарниками `gms-<os>-<arch>[.exe]` и файлом `checksums.txt`. Версия в бинарник не встраивается. README получает раздел «Установка из релизов» как основной путь установки, с инструкцией по карантину macOS; `go install` остаётся альтернативой.

## User Stories

1. Как пользователь gms без Go, я хочу скачать готовый бинарник из GitHub Releases, чтобы поставить утилиту без установки Go.
2. Как пользователь любой платформы из «Системных требований» (macOS, Linux, Windows × amd64/arm64), я хочу найти в релизе бинарник под свою платформу, чтобы покрытие совпадало с обещанным в README.
3. Как пользователь, я хочу голые бинарники без архивов, чтобы установка была «скачал → положил в PATH → chmod +x», без распаковки.
4. Как пользователь корпоративной машины, я хочу `checksums.txt` в релизе, чтобы проверить скачанный файл, прошедший прокси или зеркало.
5. Как сопровождающий, я хочу, чтобы релиз собирался и публиковался push'ем тега `v*`, чтобы публикация была одним действием, а имя тега — единственным источником версии.
6. Как сопровождающий, я хочу, чтобы перед сборкой релиза гонялся `scripts/check.sh`, чтобы тег на непроверенном коммите красил workflow вместо публикации плохого релиза.
7. Как пользователь macOS, я хочу в README инструкцию по снятию карантина, чтобы неподписанный бинарник запустился без сюрпризов Gatekeeper.
8. Как пользователь с Go, я хочу, чтобы `go install` остался в README как альтернатива, чтобы прежний путь установки продолжал работать.
9. Как пользователь, я хочу автосгенерированные release-ноты, чтобы понять, что изменилось с прошлого релиза и стоит ли обновляться.
10. Как сопровождающий, я хочу, чтобы релиз жил в отдельном workflow, чтобы `check.yml` не переусложнялся (US17 задачи 4).
11. Как пользователь, я хочу, чтобы бинарник из релиза и бинарник от `go install` вели себя одинаково, чтобы пути установки не расходились.
12. Как пользователь Windows, я хочу бинарник с расширением `.exe`, чтобы файл запускался в PowerShell без переименования.

## Implementation Decisions

- Отдельный файл `.github/workflows/release.yml`; `check.yml` не трогается (US17 задачи 4).
- Триггер: `push` тегов с шаблоном `v*`. Схема версий `vMAJOR.MINOR.PATCH`, первый релиз `v0.1.0` с коммита в `main`. Ручной запуск (`workflow_dispatch`) не добавляется: он создал бы второй путь и вопрос «откуда берётся версия» — имя тега остаётся единственным источником.
- GoReleaser отклонён: 6 целей — это матрица в ~20 строк YAML, ноль новых инструментов и конфигов; прецедент задачи 4 — явный тонкий workflow вместо готового инструмента со своими соглашениями.
- Job `check`: `ubuntu-latest`; шаги те же, что в job `check` из `check.yml` (checkout, setup-go с `go-version-file: go.mod`, `go install` gitleaks `v8.30.1`, nocomments `@latest`, golangci-lint `v2.15.0`), затем `sh scripts/check.sh` целиком. Дублирование установки инструментов в двух workflow осознанное: вынесение в composite action или reusable workflow не окупает ~8 строк.
- Job `build` (`needs: check`): матрица ровно 6 пар — darwin/amd64, darwin/arm64, linux/amd64, linux/arm64, windows/amd64, windows/arm64 — точное перечисление из «Системных требований» README; `CGO_ENABLED=0 go build -trimpath -o gms-<goos>-<goarch>[.exe] .`; артефакты через upload/download-artifact. Версия не встраивается: показать её некуда (флага `-version` нет и он не выбран), а `go install`-бинарники и так собираются без неё — расхождений между путями установки не появится.
- Job `release` (`needs: build`): единственный job с `permissions: contents: write`; складывает артефакты в `dist/`, считает `shasum -a 256` в `checksums.txt`, публикует `gh release create "$GITHUB_REF_NAME" --verify-tag --generate-notes` с файлами `dist/*`. Runner `ubuntu-latest`, `gh` на нём предустановлен. `concurrency` не нужен: теги редки, релизную сборку отменять не надо.
- README: раздел «Установка из релизов» становится основным путём — ссылка на страницу релизов, скачивание файла под платформу, PATH и `chmod +x`; для macOS — снять карантин (`xattr -d com.apple.quarantine` или разрешить в настройках); упоминание `checksums.txt` с командой проверки; для Windows — `.exe` в PATH. `go install` остаётся альтернативой, фраза «Готовых бинарников нет» убирается. Раздел правит задача 8 (граница подтверждена в `ai/6/task.md`).

## Testing Decisions

- Go-код не меняется, unit-тесты не пишутся; реализация через `/tdd` в буквальном смысле неприменима — для workflow действует тот же эмпирический стиль приёмки инфраструктуры, что в задаче 4.
- Локальная предпроверка перед пушем: сборка всех 6 целей матрицы (`CGO_ENABLED=0 GOOS=… GOARCH=… go build -trimpath …`) зелёная.
- Приёмка эмпирическая на первом релизе `v0.1.0`: push тега → зелёный workflow → релиз с 7 файлами (6 бинарников + `checksums.txt`); `shasum -a 256 -c checksums.txt` сходится; скачанный с GitHub бинарник запускается и выводит ожидаемое; на macOS проверены карантин после браузерного скачивания и снятие `xattr`.
- Красная ветка: тег на коммите с ломающим gofmt изменением красит job `check`, релиз не публикуется.
- Специальные инструменты вроде actionlint не вводятся — разовая проверка не стоит нового инструмента (прецедент задачи 4).

## Out of Scope

- Homebrew tap и Scoop: отдельный репозиторий формул и манифесты не окупаются, пока `go install` и прямое скачивание закрывают потребность; добавить позже можно без переделки workflow.
- Подпись и нотаризация (codesign/notarize для macOS, Authenticode для Windows).
- Флаг `-version` и встраивание версии в бинарник (не выбран из списка улучшений).
- Фикс Windows-тестов (`usage_test.go` / `configPath`): гейт `check` релиза гоняется только на Linux, Windows-сборка тестами не проверяется — наследие задачи 4.
- Правки `check.yml` и перенос общих шагов в composite/reusable-конструкции.
- Ручной запуск релиза, расписание, сборка из dirty-репозитория и прочие нестандартные пути.

## Further Notes

- Тег ставится вручную: `git tag v0.1.0 && git push origin v0.1.0` на коммите в `main`.
- ADR не пишется: смена инструментария релиза (GoReleaser, tap, подпись) позже — правка одного workflow, «hard to reverse» не выполнен.
- GLOSSARY.md не пополняется: релизная инфраструктура не вводит терминов домена утилиты.
- Имена job'ов релизного workflow в required status checks не попадают: защита ветки (задача 4) требует только чеки из `check.yml`.
