# Спека задачи 4: CI — проверка на GitHub Actions

## Problem Statement

Проверки репозитория (gofmt, nocomments, go vet, `go test -race`, сканы gitleaks: правила на случаях и файлы репозитория) запускает только pre-commit hook из `.githooks/`, и его нужно включать в каждом клоне вручную (`git config core.hooksPath .githooks`). Коммит, сделанный без hook, или правка через веб-интерфейс GitHub попадают в `main` непроверенными, а `go install github.com/MikhailEpatko/gms@latest` ставит пользователям ровно то, что лежит в `main`. Секреты в истории коммитов hook не видит вовсе: он проверяет только индекс текущего коммита.

## Solution

GitHub Actions workflow запускает `scripts/check.sh` целиком — тот же набор проверок, что и hook, — на каждый push в `main` и каждый pull request, на матрице `ubuntu-latest` + `macos-latest`. Gitleaks и nocomments CI ставит так же, как локальные коммитеры: `go install`. Отдельный job сканирует всю историю репозитория (`gitleaks git`) — то, чего hook и `check.sh` не делают, и то, что ADR 0004 заранее отдал шагу CI. Защита ветки `main` делает зелёные job'ы обязательными для слияния, так что непроверенный коммит в `main` становится невозможным. README получает бейдж статуса.

## User Stories

1. Как коммитер без включённого hook, я хочу, чтобы CI краснел на непроверенном коммите в `main`, чтобы проблему увидели, даже когда hook не сработал или не был включён.
2. Как коммитер, я хочу, чтобы CI запускал ровно `scripts/check.sh` и ничего сверх него, чтобы локально зелёный коммит не краснелся в CI от какой-то другой, отдельной проверки.
3. Как коммитер, я хочу, чтобы CI ставил gitleaks той же командой и версии, что в README (`go install ...@v8.30.1`), чтобы локальная установка и CI-установка совпадали, а подсказка hook в случае «gitleaks не найден» вела к рабочей команде и в CI.
4. Как коммитер, я хочу, чтобы CI ставил nocomments без закрепления версии (`@latest`), чтобы правка nocomments доходила до CI без правки workflow (ADR 0005).
5. Как автор pull request, я хочу, чтобы `check.sh` гонялся на моём PR, чтобы исправить проблемы до слияния, а не после.
6. Как автор pull request, я хочу, чтобы устаревший прогон моего PR отменялся при новом push, чтобы результат относился к последнему коммиту, а очередь не забивалась старыми прогонами.
7. Как владелец репозитория, я хочу, чтобы зелёные job'ы workflow были обязательны для слияния в `main` (branch protection), чтобы непроверенный код не попал в `main` ни через коммит без hook, ни через веб-интерфейс.
8. Как пользователь gms, я хочу, чтобы всё в `main` прошло проверки, чтобы `go install github.com/MikhailEpatko/gms@latest` ставил проверенный код.
9. Как владелец репозитория, я хочу, чтобы вся история сканировалась `gitleaks git` на каждый push и PR, чтобы секрет, проскочивший мимо hook (коммит с `--no-verify`, правка через веб-интерфейс, push protection пропускает пароль в URL и корпоративные хосты), был пойман CI.
10. Как владелец репозитория, я хочу, чтобы скан истории работал с `--redact`, чтобы секрет не появился в логах CI публичного репозитория.
11. Как владелец репозитория, я хочу, чтобы скан истории явно передавал `--config .gitleaks.toml`, чтобы переменная окружения `GITLEAKS_CONFIG` не подменила правила.
12. Как коммитер на macOS, я хочу, чтобы проверки гонялись и на Linux, и на macOS, чтобы платформенно-зависимые поломки скриптов и `-race` ловились до слияния.
13. Как случайный контрибьютор через fork, я хочу, чтобы workflow работал на PR из fork без токенов на запись, чтобы мой PR проверялся как чужой, а не падал из-за прав.
14. Как смотрящий на README, я хочу видеть бейдж статуса CI со ссылкой на прогоны, чтобы сразу знать, зелёный ли `main`, и быстро перейти к логам.
15. Как сопровождающий, я хочу, чтобы в README было видно, что CI гоняет проверки на macOS и Linux, чтобы обещание поддержки Windows не создавало ложной уверенности, что оно проверяется в CI.
16. Как автор задачи 5 (golangci-lint), я хочу, чтобы линт встал в `check.sh` и появился в CI без правки workflow, чтобы CI-файл не приходилось трогать при каждой новой проверке.
17. Как автор задачи 8 (релизы), я хочу, чтобы релизная сборка жила в отдельном workflow, чтобы этот CI не мешал и не переусложнял релизы.
18. Как коммитер, я хочу, чтобы CI ставил инструменты один раз на job и звал `check.sh` без обёрток, чтобы workflow оставался тонким и не дублировал шаги скриптов.

## Implementation Decisions

- Один файл workflow, два job.
  - `check`: матрица `ubuntu-latest` + `macos-latest`; шаги: checkout, setup-go с `go-version-file: go.mod` (версия берётся из `go.mod`, встроенный кеш сборки включён), `go install` gitleaks и nocomments в `$(go env GOPATH)/bin`, запуск `sh scripts/check.sh`.
  - `secrets-history`: только `ubuntu-latest`; checkout с полной историей (`fetch-depth: 0`); тот же `go install` gitleaks; `gitleaks git --config .gitleaks.toml --redact -v .` по всей истории.
- Скан истории вынесен в отдельный job, а не в матрицу: не гоняется дважды, у защиты ветки есть собственный чек.
- Триггеры: `push` только в `main` и `pull_request` со стандартными types; без path-фильтров — проверки дешёвые (~минута), а отбор «релевантных» файлов ломает гарантию «в `main` попадает проверенное».
- `permissions: contents: read` — минимальные права, fork-PR работают без токенов на запись.
- `concurrency` с группой по ref и отменой устаревших прогонов.
- Gitleaks ставится `go install github.com/zricethezav/gitleaks/v8@v8.30.1` — как в README и как в подсказке hook в случае отсутствия gitleaks (ADR 0004); готовый бинарник релиза и официальный action отклонены: первый требует маппинг «ОС+арх → имя файла», второй не кладёт gitleaks в `PATH`, который нужен `check-secrets.sh`.
- Nocomments ставится `go install github.com/MikhailEpatko/nocomments@latest` без закрепления версии — так решено в ADR 0005, правка nocomments доходит до CI без правки gms.
- `sh scripts/check.sh` запускается как есть, без отдельных шагов gofmt/vet/test/сканов в workflow: единственный источник правды о проверках — `check.sh` (golangci-lint из задачи 5 и всё будущее встраиваются в него без правки CI).
- Windows в матрице нет: тесты путей в `usage_test.go` ждут литералы с `/`, а `configPath` на Windows собирает путь через `filepath.Join` с `\`; правку сознательно не делаем, README продолжает обещать Windows без CI-проверки (см. User Stories 15).
- Бейдж статуса workflow добавляется в README рядом с разделом про hook и установку зависимостей; там же строка о том, на каких ОС гоняются проверки.
- Защита `main` — настройка GitHub UI, а не файл в репозитории: required status checks `check (ubuntu-latest)`, `check (macos-latest)`, `secrets-history` и запрет прямых push в `main`. Включается один раз руками после первого зелёного прогона (имена чеков должны появиться в GitHub раньше, чем их можно потребовать).
- Правки в Go-код, `scripts/` и `.githooks/` не входят: CI только запускает существующее.
- Действия GitHub пинятся по мажорной версии (`actions/checkout`, `actions/setup-go` — актуальные мажоры на момент реализации).

## Testing Decisions

- Новых швов в коде нет, unit-тесты не пишутся: задача не меняет тестируемый код.
- Хороший тест для этой задачи — реальный прогон workflow: наблюдаемое поведение (job зелёный или красный, бейдж, обязательность чеков), а не парсинг YAML локально. Приёмка эмпирическая: первый push даёт зелёные job'ы на обеих ОС, `secrets-history` находит 0 утечек на текущей истории, бейдж показывает статус.
- Локальная предпроверка перед push ограничена тем, что уже работает: `check.sh` зелёный локально (его гоняет hook), команды `go install` те же, что у коммитеров. Специальные инструменты вроде actionlint не вводятся — разовая проверка не стоит нового инструмента.
- Красная ветка проверяется дёшево: временная правка, ломающая `gofmt` или содержащая тестовый секрет, должна покрасить соответствующий job; проверяется на реальном прогоне, затем откатывается.
- Prior art по стилю приёмки инфраструктуры — `scripts/check-secrets.sh`: сквозные случаи на одноразовых репозиториях вместо ручной приёмки правил. Для workflow аналогичный каркас не строится: прогон в GitHub Actions сам и есть этот каркас.

## Out of Scope

- Windows в CI и фикс тестов путей (`usage_test.go` / `configPath`) под Windows.
- golangci-lint (задача 5) — он встраивается в `check.sh` без отдельного шага CI.
- Сборка и публикация релизов (задача 8) — отдельный workflow.
- Локальный запуск workflow (act и подобное), расписание по cron, кеш `go install`-нутых бинарников сверх встроенного кеша setup-go.
- Любые правки правил `.gitleaks.toml` и самих скриптов проверок.
- Настройка secret scanning/push protection GitHub — уже включены платформой для публичного репозитория.

## Further Notes

- Перед коммитом задачи почистить индекс: `git restore --staged scripts/nocomments` — файлы остались застейдженными от переноса nocomments в отдельный репозиторий (ADR 0005), в коммитах их никогда не было.
- ADR на это решение не пишется: добавление новой ОС или смена способа установки — правка одного места, «hard to reverse» не выполнен.
- Имена job'ов попадают в required status checks; переименование job'а позже сломает защиту ветки, пока чек не обновят в настройках.
