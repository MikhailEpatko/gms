```bash
scripts/check.sh             # все проверки: gofmt, vet, go test -race; работа готова, только когда он прошёл
go build -o gms .            # сборка бинарника
```

Тот же `scripts/check.sh` запускает pre-commit hook из `.githooks/`. В новом клоне hook подключается командой `git config core.hooksPath .githooks`.

## Что делает утилита `gms`

CLI, который для каждого проекта и каждого окружения показывает текущий деплой: дату деплоя, версию приложения и коммит деплоя.

- `gms` без флагов выводит все проекты из конфига.
- `gms -p project1,project3` выводит только перечисленные проекты (стандартный пакет `flag`). Пробелы вокруг кодов обрезаются, пустые элементы пропускаются, повторный `-p` накапливает коды, повторы схлопываются по первому вхождению. Позиционный аргумент (`gms -p project1 project3`) считается ошибкой с подсказкой `-p project1,project3`, exit 2.
- `gms -c` печатает путь к конфигу и выходит, остальные флаги игнорируются.

Порядок вывода: проекты и окружения идут в том порядке, в каком записаны в файле конфига (JSON читается с сохранением порядка ключей, не через `map`). С `-p` проекты выводятся в порядке аргументов. Между окружениями ставятся 1 пустая строка и `-`×63, между проектами 2 пустые строки и `=`×63. Линия стоит вплотную к следующему заголовку, разделители только между блоками.

```
project2
DEV:
2026-09-24 16:35:33 MSK (MR !23)
7.0.2
1abfac4b Merge branch 'XXXXX-3488' into 'dev'

---------------------------------------------------------------
DEMO:
нет деплоев


===============================================================
project1
...
```

- Дата выводится в локальной зоне, формат `2006-01-02 15:04:05 MST`. Пометка ставится, только если ref деплоя отличается от ветки окружения. Деплой из MR приходит с ref `refs/merge-requests/<N>/head` (или `.../merge` у merged results pipeline) и выводится как `(MR !<N>)`, любой другой чужой ref выводится как `(ветка: X)`.
- Коммит выводится как короткий SHA и заголовок.

### Конфиг

Путь: `~/.config/gms/config.json`, переопределяется через env `GMS_CONFIG`. Если не заданы ни `HOME`, ни `GMS_CONFIG`, это ошибка, exit 1. JSON вида `{ "<код проекта>": { "<ОКРУЖЕНИЕ>": "<url ветки>" } }`, URL вида `https://gitlab.example.com/group/<repo>/-/tree/<branch>`. Из URL извлекаются хост, путь проекта в GitLab и ветка окружения. Окружения произвольные, берутся из ключей. Если файла нет, `gms` печатает «создайте ~/.config/gms/config.json» и пример конфига с обезличенными URL (`gitlab.example.com`), exit ≠ 0.

### Откуда берутся данные

Все запросы выполняются через подпроцесс `glab api --hostname <host>` (ADR 0001). Токенов в `gms` нет.

1. **Текущий деплой** (ADR 0002): Deployments API, `environment=<ключ окружения в нижнем регистре>`, `status=success`, последний по `finished_at`. Ветка не фильтруется. Дата деплоя = `deployable.finished_at` (на верхнем уровне deployment поля `finished_at` нет), коммит = `deployable.commit.short_id` и `deployable.commit.title`. Проверено вживую на всех 12 парах 2026-10-18.
2. **Версия приложения**: строка `build_version=` из `application.version` **на коммите деплоя**, а не на HEAD ветки.

### Ошибки

- Неизвестный код в `-p`: ошибка до запросов со списком известных кодов, exit 2.
- `glab` не установлен или не залогинен: сразу выход с подсказкой `glab auth login --hostname gitlab.example.com`.
- У окружения нет деплоев: строка `нет деплоев`.
- В деплое нет `sha` или `deployable.finished_at` (например, `deployable: null`): это ошибка пары. Пустое `build_version=` считается ошибкой версии.
- Ошибка по паре проект+окружение выводится на месте этой пары, остальные пары выводятся, итоговый exit 1. Если не удалось получить только версию: строка `версия: ошибка (<причина>)`, дата и коммит выводятся.
